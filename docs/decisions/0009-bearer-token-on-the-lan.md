# 0009 — Shared bearer token for LAN access

**Status:** Accepted · 2026-09-13

## Context

To be usable from the Ubuntu PC and a phone, the server must listen on the home
network. Anything on that network can then reach it: guests' phones, a
compromised smart TV or IoT device, other people in the house. Without
authentication any of them could:

1. **control playback** — skip, pause, set the volume to 100 at 3 am;
2. **read the listening history** as it happens (`GET /api/state`);
3. **act through the owner's browser**: any web page opened on any LAN device
   can send `POST http://192.168.1.16:8000/api/next`. A POST with no custom
   headers is a CORS "simple request", which browsers send without asking the
   server first — a *cross-site request forgery* (CSRF).

There is one user and no user management is wanted (see non-goals).

## Decision

- **One shared secret token**, generated by `music-server init` with Python's
  `secrets` module (32 random bytes, 43 characters) and stored in a per-user
  config file outside the repository (`%APPDATA%` / `~/.config`). The server
  refuses to start without one, or with one shorter than 32 characters.
- **Every `/api` route requires `Authorization: Bearer <token>`**, enforced by
  a single FastAPI dependency on the API router. `/health` and the static web
  files stay public: they hold no secrets and change nothing.
- **Constant-time comparison** (`secrets.compare_digest`) so response timing
  can't leak the token character by character.
- **Header, not cookie.** A custom `Authorization` header makes any cross-site
  request trigger a CORS preflight, which the server doesn't approve, so the
  CSRF scenario above is blocked without extra machinery. A cookie would be
  sent automatically by the browser and need separate CSRF protection.
- **The web page** keeps the token in `localStorage`. Pairing uses a link
  `http://<host>:8000/#token=…`: the fragment after `#` is never sent to the
  server (so never logged), and the page removes it from the address bar.
- **Defence in depth for the page:** a Content-Security-Policy allowing only
  same-origin resources and forbidding framing, alongside `textContent`-only
  rendering of track data.
- **Network scope:** the server listens on `0.0.0.0`; a Windows Firewall rule
  allows TCP 8000 only on *Private* networks and only from the local subnet.
- **The CLI** reads the token from the config file or environment only, never
  from a command-line option (visible in `ps` and shell history).
- Failed authentication is logged with the client address; the token is never
  logged.

## Consequences

- Someone on the Wi-Fi without the token gets `401` for every command.
- **Accepted risk — no TLS.** Traffic is plain HTTP, so someone able to capture
  and decrypt the Wi-Fi traffic (e.g. another client on the same WPA2 network)
  could read the token. HTTPS with a self-signed certificate is awkward on
  phones and needs certificate management; for a home music remote this is
  judged not worth it. The consequence of a leaked token is limited to music
  control, and `music-server init` on a fresh file rotates it.
- A 256-bit random token can't be guessed, so no rate limiting is needed.
- Each new client needs the token once (config file line or pairing link).
- The token is readable by JavaScript on the page; the CSP and text-only
  rendering are what keep injected scripts out.
